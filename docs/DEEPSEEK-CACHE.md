# DeepSeek 前綴快取（1.3.2）

1.4.0 沿用此帳本及用量統計，並加入 [自主與順序工作計畫](DEEPSEEK-WORK-PLANS.md)。工具定義已擴充，升級後會建立新的前綴；檢查商店等多輪工具交換亦逐次記錄原文。下方實測數據專屬 1.3.2，不能當成 1.4.0 的遊戲命中率。

DeepSeek 官方 API 預設啟用前綴快取。模組不需額外開啟開關；相容 API 是否提供快取及用量欄位，取決於該服務。[官方快取說明](https://api-docs.deepseek.com/guides/kv_cache/)

## 請求排列與歷史

固定 system 訊息只包含角色性格、能力與執行規則。每輪在既有完整訊息後追加最新 `CURRENT_CONTEXT`（偏好清單、商店／員工狀態、回覆語言）和玩家訊息。舊的狀態摘要保留原文，並明確標示只以最新摘要為準。

模型的原始工具要求、各個 tool 結果及回覆亦保留，下一輪沿用已送出的前綴。語言、記憶或遊戲時鐘改變，不會重寫前面的訊息。這個 API 帳本只在記憶體中存在；不增加商店記憶檔的格式或把遊戲快照另存到磁碟。

新開房間／重啟時，從原有最近 40 則對話中保留最新最多 16,000 字元作起始內容；一般短對話可全部保留。原始帳本達到 20 個完整 turn 或 32,000 個序列化字元後，成批移除較舊 turn，通常降至 10 turn／16,000 字元以下，再接續新對話。只移除完整工具交換，避免孤立 tool_call_id。縮減後命中率可能暫時下降。

切換商店、重新綁定、清空記憶、變更角色性格或 API／模型／金鑰時會重建相應對話。單純重新儲存相同 API 網址及模型且未輸入金鑰，會保留帳本和統計。長期偏好、API 設定、員工綁定及原有 40 則顯示記錄仍維持原機制。

## 工具結果追問

第一輪與結果追問都維持相同 `tools` 定義及 `tool_choice=auto`。追問追加 `FINAL_RESPONSE_ONLY` 指令，只要求總結已發生的結果；程式端的最終回覆階段會拒絕任何新工具要求，絕不再執行派工或記憶工具。此限制只適用於當前回合；下一個 `CURRENT_CONTEXT` 明確結束舊限制，新一輪可依玩家的新指令使用工具。

初步真實 API 測試發現，改成 `tool_choice=none` 的追問雖然仍提供工具定義，回報的 prompt token 數及快取重用行為仍不同，該次追問為 0 hit。最終設計因此固定 `auto`，並保留程式端執行限制。這是依該次測量所作的選擇，不代表所有相容服務的內部格式相同。

取消或出錯時，帳本會記錄請求已結束；若有尚未執行的工具，會補上「未執行」結果，不能將它當成成功，下一輪亦不得重試舊指令。

## F7 數據

記憶欄下方顯示四行用量：

- 本次回覆的 cache 命中率及 `H`（hit）／`M`（miss）輸入 token。
- 本房間累計命中率和 hit／miss tokens。命中率為 `sum(hit) / sum(hit + miss)`，不平均每次的百分比。
- 本次輸入／輸出 tokens 及整個非串流回覆的時間（ms），不是首 token 時間。
- API 回覆數與未提供快取統計的回覆數。一次派工可能有兩次 API 回覆，兩次各自計入。

優先讀取官方 `usage.prompt_cache_hit_tokens`／`prompt_cache_miss_tokens`，亦支援 `prompt_tokens_details.cached_tokens` 加 `prompt_tokens` 推算 miss。欄位不存在或不一致時顯示「未提供」，不猜測為 0%。累計比例只納入有效快取統計，未報數量另外列出。[官方 usage 欄位](https://api-docs.deepseek.com/api/create-chat-completion/)

房間及 API 設定變更後統計重新計算。日誌 `Companion API usage` 只記錄輸入／輸出、hit／miss 及耗時，不記錄金鑰、請求正文或對話內容。HTTP／網路失敗而沒有解析出 API 回覆時，不會憑空估算用量。

這是小型合成測試，不是完整遊戲負載的 A/B 基準。不能由此宣稱遊戲固定有 60.8% 命中、一定省下相同比例費用，或已證明速度提升。快取由服務端盡力提供，存在建構延遲及過期；實際遊戲結果以面板回報為準。模組不為追求命中率補入無用文字，也不在背景發送暖快取請求。
